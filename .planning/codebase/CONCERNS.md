# Codebase Concerns

**Analysis Date:** 2026-10-06

## Tech Debt

**Monolithic Frontend Views:**
- Issue: Views and modals contain large inline blocks of JSX and embedded logic exceeding 1,200 to 2,400 lines per file.
- Files: `frontend/src/views/AcademicsView.tsx`, `frontend/src/views/AIPlannerView.tsx`, `frontend/src/App.tsx`, `frontend/src/components/LeetCodeDashboard.tsx`
- Impact: High cognitive load during maintenance, slower IDE indexing, difficulty isolating rendering regressions.
- Fix approach: Extract nested tabs, modals, and charts into standalone subcomponents in `frontend/src/components/academics/`, `frontend/src/components/aiPlanner/`.

**Massive Hardcoded Seed Data:**
- Issue: `defaultData.ts` contains 4,555 lines of hardcoded mock student records, semester grades, and timetable structures.
- Files: `frontend/src/services/defaultData.ts`
- Impact: Inflates client bundle size and slows initial bundle parsing on low-end mobile devices.
- Fix approach: Split into dynamic mock fixtures loaded asynchronously or fetched via static JSON assets under `frontend/public/data/`.

**Custom Minimal Test Runner Limitations:**
- Issue: `run_without_pytest.py` fails on 35 tests due to incomplete fixture resolution (`LookupError: no fixture named 'result'`), even though the standard `pytest` runner executes all 400 tests cleanly.
- Files: `backend/tests/run_without_pytest.py`
- Impact: Developers without `pytest` installed receive false test failure alarms.
- Fix approach: Upgrade fixture resolution in `run_without_pytest.py` to support parameterized fixtures or standardize entirely on `pytest`.

## Known Bugs

**Intermittent VTOP Captcha OCR Misrecognitions:**
- Symptoms: Captcha validation error response from VTOP during login despite valid credentials.
- Files: `backend/app/vtop/ocr.py`, `backend/app/vtop/session.py`
- Trigger: Highly noisy background lines or unusual font kerning generated by the VTOP portal captcha engine.
- Workaround: Backend retries login up to 3 times with fresh captcha challenges automatically.

## Security Considerations

**Live Session Cookies on Shared Networks:**
- Risk: Exposing backend on `0.0.0.0:8000` on a public campus Wi-Fi exposes active VTOP session cookies to nearby users.
- Files: `backend/app/main.py`, `run_backend.sh`, `start_local.sh`
- Current mitigation: Documentation and scripts default to binding strictly to loopback `127.0.0.1`.
- Recommendations: Add runtime check warning if host is set to `0.0.0.0` outside of Docker environment (`os.path.exists('/.dockerenv')`).

**Unencrypted Disk Storage of Cached Stores:**
- Risk: `backend/data/store_{reg_no}.json` contains parsed student academic records in plaintext.
- Files: `backend/app/storage.py`
- Current mitigation: Password hashes/credentials are discarded and not persisted in stores.
- Recommendations: Implement optional file encryption using `auth_crypto` or OS keychain when persisting sensitive student profiles.

## Performance Bottlenecks

**Sequential Multi-Page VTOP Portal Scrape:**
- Problem: Full sync takes 10–25 seconds on initial login.
- Files: `backend/app/vtop/scraper.py`, `backend/app/routers/auth.py`
- Cause: Multiple separate HTTP requests needed to fetch profile, timetable, attendance, marks, and exam schedules sequentially.
- Improvement path: Parallelize independent page requests using `httpx.AsyncClient` or a thread pool after session cookie establishment.

**Render Free Tier Cold Starts:**
- Problem: Initial API response delay of 30–50 seconds after inactivity.
- Files: `render.yaml`, `Dockerfile.backend`
- Cause: Render free tier spins container down to zero after 15 minutes of idle time.
- Improvement path: Deploy a lightweight heartbeat ping or upgrade to Render Starter / Vercel Serverless production instance.

## Fragile Areas

**VTOP DOM Table Parsing:**
- Files: `backend/app/vtop/parser.py`
- Why fragile: The scraper depends on exact HTML table headers and column indices. Any portal UI redesign by VIT breaks parsing.
- Safe modification: Update `backend/tests/fixtures/vtop_pages.py` with newly captured HTML, run `pytest backend/tests/test_vtop_parser.py`, and adjust parsing selectors before deploying.
- Test coverage: Covered by 100+ contract tests against recorded DOM fixtures.

**Moodle LMS Course Code Extraction:**
- Files: `backend/app/course_verification.py`, `backend/app/routers/lms.py`
- Why fragile: Faculty frequently format course titles with non-standard abbreviations, missing slashes, or custom slot codes in LMS.
- Safe modification: Verify regex heuristics against sample courses using `test_course_verification.py`.
- Test coverage: Extensive fuzzy match test suite in `test_course_verification.py`.

## Scaling Limits

**File-Based Student Store (`backend/data/`):**
- Current capacity: Single-student / demo deployment (~tens of users).
- Limit: File system concurrency locks and storage degradation if hundreds of concurrent students write to local JSON files simultaneously.
- Scaling path: Migrate store persistence fully to Supabase PostgreSQL (`user_courses` and `profiles` tables).

## Dependencies at Risk

**Tesseract OCR Binary (`tesseract-ocr`):**
- Risk: System dependency requiring native binary and language data files (`tessdata`).
- Impact: Environment portability friction if running on serverless runtimes that do not support arbitrary Linux packages.
- Migration plan: Maintain containerized Docker runtime for Render; evaluate lightweight WebAssembly OCR or server-side ONNX vision models as pure Python alternatives.

## Missing Critical Features

**Push Notifications for Attendance Shortages:**
- Problem: Students must manually check the dashboard to discover that attendance dropped below 75%.
- Blocks: Real-time alerts before scheduled classes.

## Test Coverage Gaps

**Live Portal Redesign Drift:**
- What's not tested: Real-time upstream changes to VTOP markup that differ from static HTML fixtures.
- Files: `backend/app/vtop/scraper.py`, `backend/app/vtop/parser.py`
- Risk: Portal breaks in production while test suite still passes against old fixtures.
- Priority: High (periodically validate with `backend/scripts/run_live_e2e_test.py`).
